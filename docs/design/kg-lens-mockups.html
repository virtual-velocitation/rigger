kg explorer · design direction

One lens, one subject. Everything else is metadata.

The defect in the current canvas: it renders the storage taxonomy - per-type buckets like code-entity (4280) and per-file spokes - as if they were knowledge. The fix is a discipline, applied per lens: the graph shows only the lens's subjects and the typed relationships between them. Files, concepts, and memory still exist everywhere, but as metadata on the node you're inspecting - in the hover card and the subject view - never as nodes competing in the layout.

On the graph · subjects

  • Code lens: functions, types, traits - calls / contains / implements
  • Files lens: files - uses, weighted by coupling
  • Concepts lens: concepts - co-evidence

In the card · metadata

  • Defining file + line
  • Concepts the node evidences
  • Memory: decisions, findings
  • Degree, community, peers

Never rendered

  • Schema names as nodes (code-entity, file, decision)
  • Per-type bucket hubs with counts
  • Cross-taxonomy spokes (file → entity)

lens 1 of 3

Code lens - the code's own structure

Subjects are entities: functions (circles), types (squares), traits and contracts (diamonds). Edges are directed and labeled. Coupling communities survive as quiet hulls behind the nodes - grouping, not hubs. Hovering emit_keyed_batch raises the metadata card; nothing about files enters the layout.

  1. The card is where the other taxonomies live. File and line, concept chips, and memory counts appear on hover; clicking a chip pivots the relevant lens to it.
  2. Communities are hulls, not hubs. The Leiden grouping tints a region behind its members. Nothing radiates from a bucket node, so density stays local and readable.
  3. Edges carry their type. Solid directed = calls; dashed = structural (implements, contains, creates). The layered calls view keeps its own layout, unchanged.

lens 2 of 3

Files lens - coupling between files

Here files are legitimately the subjects. Node size is entity count, edge weight is coupling strength, hulls are directories. The code inside a file is this lens's metadata: the hover card lists the file's top entities and hands off to the code lens.

  1. Lens handoff, subject preserved. Clicking an entity in the card switches to the code lens focused on that entity - the two taxonomies connect through navigation, not through edges drawn on one canvas.

lens 3 of 3

Concepts lens - intent, sized by evidence

Subjects are the derived concepts. Node size is evidence weight; edges join concepts that share evidence. The entities and files behind a concept are the card's metadata, with the same handoff into the code lens.

drill-down · any lens

Subject view - click a node, get its world

Clicking a node focuses it as the subject: the canvas re-seeds to its one-hop neighborhood, and the memory rail docks on the right with the decisions and findings that govern it. This is where the run's knowledge attaches to the code - as a rail, never as nodes in the layout.

shared behavior

Interaction model, all lenses

hover
Metadata card. File + line, concepts, memory counts, degree. Neighbors highlight; everything else dims.
click
Focus as subject. Re-seed to the one-hop neighborhood, dock the memory rail.
card chip click
Lens handoff. A file chip opens the files lens on that file; a concept chip opens the concepts lens; an entity opens the code lens. The subject rides along.
overview zoom
Communities, not buckets. Zoomed out, hulls collapse to labeled community nodes sized by member count - a knowledge grouping. Storage types are never a grouping key at any zoom.
