# Graph vs grep: the operator's own lookups, measured (2026-09-11)

Why this exists: the operator's Claude Code session reached for `grep` instead of the
knowledge graph for 22 of 52 code lookups on 2026-09-08..11, and when asked why, offered "the
graph felt less reliable". That reading translates to "grep outperforms rigger", which is
either a damning product finding or a rationalization. Measured rather than argued: every
grep-only lookup that was a genuine code-knowledge question (12 of the 22; the other 10 were
literal-text checks such as em-dash counts, test-result lines and process listings) was
re-asked through `rigger ground <query> 6` and, where an entity name was known, `rigger graph
--show <name>`, against the same tree, scored on whether the first page answered, whether the
location was fresh, and what the graph added that grep cannot.

Timing: every `ground` call answered in 0.1 to 0.7 s and every `--show` in under 2.5 s, on a
machine at load average 125 where a single grep over the tree took longer. Speed was never
the reason.

## Findings

1. **Staleness is the defect, not the model.** Three of the four "found" entities carry a
   line pointer the tree no longer matches, and one function added by spec 86 is absent
   altogether: the index lags integrations by at least two specs. A pointer that is wrong
   on arrival is what makes an operator stop trusting the tool, and it is the only finding
   here that matches the "felt less reliable" excuse. Every integration must reindex the
   files it lands, and `graph --show` must resolve a name in the current tree rather than
   print a recorded line.
2. **Coverage stops at Rust.** The driver script (`workflows/rigger.js`) and the workflow
   definition are where two of the twelve questions lived. They are part of the product and
   belong in the graph.
3. **Ranking is lexical.** `ground` ranks a bare identifier match (`run`, `new`, `tests`)
   above intent; questions 3, 5 and 6 drowned in generic tokens. An exact-name boost and a
   penalty for tokens that occur in hundreds of files would have answered 3 outright.
4. **Two of twelve are grep's by design.** A negative ("does anything handle X") and a
   string-literal site are not graph questions; the rule is graph first for "where/how does
   X work", grep for literal text, and a recorded KG gap when the graph should have answered
   and did not.
5. **Where it worked, it gave more than grep.** Questions 10, 11 and 12 came back with
   degree and neighbours; grep came back with lines. The operator never used that surplus
   because the pointer beside it was stale.

## What changes

- Spec 92 (graph freshness, coverage, ranking, and the graph as a first-class session tool
  with a lookup hook) - queued after the resource-consumption specs 91 and 89 by operator
  order, ahead of everything else.
- The operator session rule, enforced by tooling rather than text: `rigger_ground` and
  `rigger_graph` as MCP tools in the session, and a hook that bounces a code-lookup grep in
  this repository to the graph the way the kill hook bounces kill.
- This document is regenerated by hand only; it is a measurement of one day, not a guard.
