# rigger-resume-a-run

## Procedure

Diagnose first: `rigger status` (or the dashboard) shows each in-flight agent's last progress report and heartbeat age. A stale heartbeat with no recent store event means the DRIVER died mid-run (quota ran out, the process crashed, the machine slept) - it does not mean the run itself is broken; the event log already holds every decision and gate verdict the run made before the driver stopped. Under an open hold the heartbeat age stops at the hold's start, so a driver that dies inside a hold never reads stale there: `rigger watch` reads the heartbeat on wall clock and names it.

A `rigger run` driver that died needs no hand relaunch. A hold (`rigger hold --reason <text>`) stops a run and Ctrl-C stops its driver: a held run launches nothing, a driver that ends while the hold stands is relaunched by `rigger release` alone, and an interrupted driver is never relaunched. Ending a driver's process any other way is a death, and the next `rigger status` (not `--line` or `--json`) or session start (`rigger prime`) brings it back by adoption, as `rigger release` and `rigger resume-unit` do, each invoked from the main checkout, and as the next login does for a run started with `--relaunch-at-login`; no other command relaunches it. The relaunch adopts the run in the background, resolving the store, scratch and state roots the dead driver resolved and finding its tools on the search path (`PATH`) it had, and says so in one line on stderr, naming its pid and the file its output goes to (`.rigger/driver.out`, which `rigger status` names while it holds what a relaunched driver said before it ended, and a driver started by hand removes). `rigger watch` relaunches nothing: it names the dead driver and `rigger status` as what brings it back, and it reports every open hold no probe ends, an operator hold or the conductor's fault hold, driver or no driver, naming who resolves it and how. A driver that returned is never relaunched, save one that ended with its run held for the orchestrator or a person, which `rigger release` relaunches: one that parked on an operator hold, and one that ended on a fault of the conductor's own, a spawn the API refused included, which holds the run naming the fault and exits non-zero. A driver that dies again within ten minutes of its relaunch, a relaunch that never started, or one whose recorded binary no longer exists is left stopped, and the line names the command that relaunches it by hand. A driver that gave its agents the login token in `RIGGER_CLAUDE_CODE_OAUTH_TOKEN`, or drove the server store named in `KURRENTDB_CONN` or by `--conn`, is relaunched only from an environment that sets that variable too; from any other, the line names that command and nothing is relaunched. A run started with `--relaunch-at-login` also registers a login entry with the OS's login-start facility (a systemd user unit on Linux, a LaunchAgent on macOS, a script in the Startup folder on Windows) while the run is live, so a machine that reboots mid-run brings the run back at the next login, with no session opened: the entry runs `rigger run --at-login <project root>`, which relaunches a dead driver as `rigger status` would and removes the entry once no relaunch is owed. A driver that ends on its own or is refused removes its entry as it empties its record, save one that ended with its run held for the orchestrator or a person, whose entry stands with its record; a run started without the flag registers nothing, and a login removes the entry an earlier launch of it left. A login also removes the entry of a project on a volume not mounted at that login; its run comes back by the usual relaunch at the next session start or `rigger status`, and registers its entry again. Each launch with the flag and `rigger setup` remove an entry whose program was since uninstalled or moved, one line naming its key and program, and name in one line, leaving it, an entry under rigger's key that is not in the form rigger writes; an entry they cannot read is named in one line with its path and the error and left while the rest are swept, and a directory they cannot list is named the same way and none is swept, failing neither, and a host with no login-start facility leaves `rigger setup` silent.

When that line says the run was left stopped, or a driver was stopped on purpose, relaunch the same driver on the same spec WITHOUT `--fresh` - `rigger run <spec> --base <ref>`, in the background as before. Because the run lives in the event log, not in the dead process, the conductor's own run-starting step adopts the existing run instead of minting a new one: it replays the log, rebuilds its in-memory state, and continues exactly where the dead driver left off. No unit restarts from zero and no work already recorded is lost.

`--fresh` is for a DIFFERENT situation, not this one: a run wedged in a terminal state (for example a plan-critique escalation) on a spec that is otherwise UNCHANGED. It is a one-shot new-run boundary, never the default way to continue interrupted work.

A run its plan-critique gate stopped on a spec defect (its halt opens `amend the spec and relaunch`) is never adopted by a command naming its spec: amend the spec, critique it with `rigger critique <spec>`, then relaunch on it, which begins a new run with no `--fresh`.

A run that is HELD, not dead, launches nothing until the hold ends, and its driver decides what ends it. A `rigger run` driver stays alive through the hold, and a passing probe ends an outage hold by itself, save a `model_not_found` hold, which runs none. `rigger release` ends any hold at once. No probe ends one you declared with `rigger hold --reason <text>`: `rigger release` does, as do the start of a new run and a `rigger run` run reaching done. A release with no hold open records nothing and says so. A hold outlives its driver: no check relaunches a held run, a relaunched driver that finds an operator hold parks its next launch and ends, and `rigger release` relaunches the run. A fault of the conductor's own that ends its drive (a plan landing that fails, a unit worktree it cannot make, a spawn the API refuses) holds the run the same way, naming the fault, and the driver exits non-zero.

A hold for a conductor fault or a refused request is YOURS to resolve first, as the orchestrator, the session that launched the run and watches it: `rigger watch` reports it as a hold for the orchestrator, and `rigger status` prints the fault under it. Read that fault. Fix its cause at the root, and never weaken a guard, a gate or a criterion to get past it. Then run `rigger release`, which relaunches the run. If the same fault holds the run again after your release (the same cause and the same first line of the fault), your fix did not hold and the hold is now for a person: `rigger status` lists it under what needs you, so stop and tell them exactly what you tried. A different fault after a release is yours to resolve again.

## Anti-move

Do not reach for `--fresh` reflexively just because a run looks stuck: on a merely-interrupted run it abandons the adoptable state your relaunch would otherwise have continued from, in exchange for nothing - reserve it for the genuinely wedged-terminal case above.

## Operator binary boundary

An agent never installs, replaces, or modifies the operator's installed `rigger` binary - that binary is operator-only. A tree checkout's own `rigger` build is invoked only by explicit path, and only to render (spec/docs output) - never to overwrite what is on PATH.
